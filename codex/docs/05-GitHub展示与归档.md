# 05 · GitHub 展示与工程归档

## 展示怎么组织

Codex 在原私有仓库内增加独立的 `codex/` 目录，并在仓库首页增加入口。Claude 的既有作品与过程记录继续作为来源主线。展示页先放 30 秒融合版，再放 27 秒独立版，配有成片链接、片尾预览、9 秒静音精选动图和画面对比。

过程文档分成粗剪判断、声音与片尾、融合新版、复现验证和本篇归档记录。提示词、参考图、生成任务摘要、时间线、脚本和媒体散列分别放到对应目录，避免只有成片、没有制作依据。

展示中的归属分别写明尚尚、Claude、Codex 和 MiniMax H3 的贡献；成功导出、技术核查与尚尚最终审美验收分别记录。

## 实际操作顺序

1. 确认当前 GitHub 身份、私有仓库和 `main` 的实际提交，读取 Claude 的最新过程记录。
2. 通过补取浅克隆缺少的祖先提交，正常快进到 Claude v3.2；保留主线文件。
3. 复制两版成片、Codex 的两个生成结果、参考图与展示图片；原始粗剪和 Claude 的视频引用仓库现有文件。
4. 把两个剪辑脚本改为从仓库相对路径读取素材；新增依赖清单与 Windows 运行入口。
5. 分别从仓库脚本重跑 v2 和 v4；检查时长、帧数和全片解码，记录重渲染与已交付文件不完全相同的事实。
6. 核查 Markdown 本地链接、Python 语法、媒体散列、凭据样式字符串和个人工作区路径。原始 API 响应含临时下载地址，只整理脱敏摘要。
7. 提交并正常推送到 `main`；通过 GitHub API 回读展示页，并核对 17 项二进制媒体的远端 Git 对象、大小与本地 SHA-256。
8. 创建专门的发布标签与 Release，附上媒体校验清单，使用 GitHub 自动生成的完整仓库 ZIP 交付工程。

## 大包上传为什么改了

最初准备把本机已有的两个工程 ZIP（约 24.8 MB、54.4 MB）单独上传为 Release 附件。当前网络上传这两个包很慢，草稿附件未完成。随后停止本轮上传进程，清理本轮未完成的草稿附件。

最终使用 GitHub 根据发布标签生成的 **Source code (zip)**。生成成片所需的原始粗剪、Claude v3 / v3.2、Codex 新增素材及脚本已经在 Git 中，两版脚本也已用这些路径实际重跑。因此完整仓库 ZIP 可以交付复现所需内容，无需再上传重复素材。分层音轨按脚本生成。

Release 附件 `MEDIA-SHA256.json` 对应 [二进制媒体清单](../manifests/artifacts.json)。清单记录单个作品和素材的 SHA-256，没有声称已经下载并计算整个 GitHub 自动 ZIP 的散列。

## 访问与凭据

制作时仓库是私有的；之后总指挥决定公开，展示页和下载现在任何人都能访问。发布没有调用新的生成任务。文档、脚本和清单没有写入 API 密钥、GitHub 令牌或临时签名下载地址。
